# Performance check, November 2026

Machine: Intel Core i7-1165G7, Intel(R) Iris(R) Xe Graphics (GL renderer string), Windows 11. `GpuClassifier` rates it
**Recommended** from the renderer string. Display adapters: the Iris Xe drives the built-in screen
(`DISPLAY1`, primary, 1536x864 at 125% scaling); the other two screens (`DISPLAY5`, `DISPLAY6`, 1920x1080) run
through "DisplayLink USB Device" adapters, which `DisplayAdapterInfo.IsUsbDisplayAdapter` matches.
Which of `DISPLAY5` / `DISPLAY6` each adapter drives was not determined; both are non-primary, so both are
treated as USB displays. The window was verified on `DISPLAY6` for the USB run at -1900,0; the `DISPLAY5` run was placed at
2000,0 (inside `DISPLAY5`'s bounds) but not verified by a window-rectangle query.

## How it was measured

- Release build, 1280x800 window, `Universe3D.App.exe --bench <csv> [--bench-at X,Y]` (see `MainWindow.Bench.cs`).
- The camera spins at 45 degrees per second the whole time, so every composition frame re-renders (the app
  otherwise renders on demand and a static scene is not a frame rate).
- Per configuration: load the data set and fly to its framing distance, 2 s warm-up, then 6 s of frame
  intervals (time between GL render callbacks, `Stopwatch`). The table gives the **median fps** (1000 / median
  interval). Arrows off, then on ("Observed" mode, the default).
- Data: built-in snapshots for Local Volume, Nearby universe and clusters; quasars from a full Milliquas
  snapshot (`--quasar-cap 2147483647`, 955,153 objects) installed temporarily in the download cache. The
  quasar limit box takes the first N objects (snapshot sorted brightest first). The cache copy was deleted afterwards.
- Frames come from WPF's composition loop, so the figure is bounded by the display/composition rate (the OS
  reports 60 Hz for the built-in screen, yet medians of 72-79 fps were seen on light scenes). Treat values above
  about 60 as "not GPU-limited" rather than literal. Run-to-run noise on light scenes is large (see runs 1 and 2).

## Spec targets (spec section 1, recommended system, built-in display)

Galaxy and cluster data sets >= 50 fps; quasars >= 30 fps with 250,000 shown, usable (>= 20 fps) with all.

All recommended-class targets are met on the built-in display, with arrows on or off. The tightest margin is
Local Volume in run 1 (54.9 fps, an unusually slow pass; run 2 gave 75.6). The GPU is the limit only for the large
quasar sets with arrows on; arrows roughly halve the 250,000-point rate. The USB displays showed no systematic
penalty here.

## Recheck after Task 12 (galaxy shapes, cluster spheres, Milky Way, scale rings)

Same machine, method and window as above (Release build, 1280x800, built-in display at 128,8, spin at 45 degrees
per second), with every new layer on: galaxy shapes (cap 20,000), cluster spheres, the Milky Way disk and Sun
marker, and the scale rings with their labels. Because the camera spins, the shape selection runs on the CPU every
frame. Quasars come from the built-in snapshot only (250,000), so "All" here also means 250,000; the full
955,153-object case was not rerun (quasar data sets have no shapes, spheres or extra per-object work).

The framing views put few galaxies above the 4 px shape threshold, so three zoomed rows were added to the bench:
the Local Group (camera 0.5 Mpc from the Sun), the Milky Way and Magellanic Clouds filling the view (0.03 Mpc,
the camera partly inside the Milky Way's bounding sphere, so it draws a full-screen impostor), and the nearby
universe at 5 Mpc. Even there, the real catalogs put only 3-12 shapes on screen at once: few galaxies are wider than
4 px at these distances. The selection pass itself is covered by `ShapeSelection_NearbyUniverseSizedInputUnder5ms`
(43,535 synthetic galaxies, thousands eligible: median 2.4 ms in a Debug test build).
